# Harness: fluxo SDD v2 (sub-projeto B) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Colocar git (branch por Spec, commit por onda, PR), loop de review por onda + final, emendas em Spec aprovada, ciclo de Status Spec↔backlog e template de CI dentro do fluxo do harness.

**Architecture:** Regras de git centralizadas em `.claude/workflows/git-flow.md` (mesmo padrão do `context-resolution.md`), citadas pelos comandos. Emendas viram a regra 3 do hook `spec-gate.mjs`, reaproveitando o cálculo antes/depois da regra 1. O loop de review vive no `/hands-on` (orquestrador) e usa o subagente `reviewer` existente.

**Tech Stack:** Markdown (comandos/skills/agentes, português), Node ≥ 18 ESM sem dependências (hook + testes `node:test`), GitHub Actions YAML (template de CI), Mermaid CLI via `npx` (diagrama).

**Spec:** `meta/specs/2026-09-28-fluxo-sdd-v2-design.md`

**Decisão do plano (não explícita na spec):** `/recheck` também commita (`docs(spec): conclui <slug>`) quando fecha a Spec — sem isso a transição `approved → done` ficaria sem commit no branch da Spec.

## Global Constraints

- Textos do harness em português, no estilo dos arquivos existentes.
- Zero dependências novas; testes com `node:test` + `node:assert/strict`; comando: `node --test "meta/tests/*.test.mjs"`.
- Nenhum comando do harness instrui `git add -A`, `git add .` ou `git commit -a` (só proibições podem citá-los).
- Branch da Spec: `spec/<slug>`, `<slug>` = nome do arquivo da Spec sem `YYYY-MM-DD-` e sem `.md`.
- Mensagens: `docs(spec): <título> (review)`, `docs(spec): aprova <slug>`, `<tipo>(<escopo>): <slug> — onda N (T1, T2)`, `docs(spec): conclui <slug>`; corpo `Spec: <caminho>` e `Cobre: FR-…`.
- Loop de review: máximo 3 rodadas por onda; review final com 1 rodada.
- Reason do ask de emenda, exato: `Emenda em Spec aprovada — registre o que mudou e por quê em ## Emendas.`
- Linha de conclusão: `**Concluído em:** YYYY-MM-DD`, logo abaixo de `**Status:** done`.
- Arquivos em LF (`.gitattributes` já força); rodar `node meta/tests/check-eol.mjs` antes de commitar.
- Stage só caminhos explícitos; `untitled.md` (se existir) nunca entra em commit.
- Commits terminam com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` (ou o modelo que de fato escreveu).

## Review Focus

- Emenda que só adiciona a seção `## Emendas`/`## Notas de Review` numa Spec antiga que não tinha a seção (com linha em branco antes) — não deve pedir. Teste na Task 1.
- Spec aprovada em CRLF com edição só de checkbox — não deve pedir. Teste na Task 1.
- `/hands-on` com working tree suja por arquivo **não rastreado** do usuário — não deve bloquear nem commitar o arquivo. Coberto pelo texto da Task 5 e conferido na review.
- `/spec` rodado já dentro de `spec/<outro-slug>` — deve perguntar, não empilhar a Spec nova no branch errado em silêncio. Texto da Task 4.
- Onda cuja review estoura 3 rodadas — nada é commitado e o humano recebe os achados abertos. Texto da Task 5.

```js
  // --- Regra 3: emenda em Spec aprovada -------------------------------------
  // Numa Spec approved, compara o conteúdo NORMATIVO antes/depois. Não conta
  // como emenda: marcar checkbox, blocos de Pendência Manual, as seções
  // "## Notas de Review" e "## Emendas", e as linhas Status / Aprovado por /
  // Concluído em (approved → done é permitido). Sem texto computável → não pede.
  if (beforeStatus === "approved" && afterText != null) {
    const normativo = (t) => {
      const out = [];
      let inSecaoLivre = false;
      let inPendencia = false;
      for (const line of t.split("\n")) {
        if (/^## /.test(line)) {
          inSecaoLivre = /^##\s+(Notas de Review|Emendas)\s*$/.test(line);
        }
        if (inSecaoLivre) continue;
        if (/^\s*>\s*🟡 Pendência Manual:/.test(line)) {
          inPendencia = true;
          continue;
        }
        if (inPendencia) {
          if (/^\s*>/.test(line)) continue;
          inPendencia = false;
        }
        if (/^\s*\*\*(Status|Aprovado por|Concluído em):\*\*/.test(line)) continue;
        out.push(line.replace(/^(\s*[-*]\s+)\[[xX ]\]/, "$1[ ]").trimEnd());
      }
      return out.join("\n").replace(/\n{3,}/g, "\n\n").trim();
    };
    if (normativo(beforeText) !== normativo(afterText)) {
      process.stdout.write(
        JSON.stringify({
          hookSpecificOutput: {
            hookEventName: "PreToolUse",
            permissionDecision: "ask",
            permissionDecisionReason:
              "Emenda em Spec aprovada — registre o que mudou e por quê em ## Emendas.",
          },
        }),
      );
      ok();
    }
  }
```

(O `"$1[ ]"` é substituição com regex e grupo intencional sobre texto do próprio arquivo — não é `new_string` do usuário, por isso não tem o problema de `$&` da regra 1.)

````markdown
# Fluxo git do harness

Regra única de branch, stage e commit usada por `/spec`, `/approve`,
`/hands-on`, `/back`, `/front` e `/recheck`. Os comandos citam este arquivo
em vez de repetir as regras.

## Branch padrão

`main` se existir; senão `master`. Com remoto, prefira
`git symbolic-ref --short refs/remotes/origin/HEAD` (sem o prefixo `origin/`).

## Branch da Spec

`spec/<slug>` — `<slug>` é o nome do arquivo da Spec sem a data
`YYYY-MM-DD-` e sem `.md`.
Exemplo: `docs/specs/2026-10-01-login-social.md` → `spec/login-social`.

## Stage explícito

**Nunca** `git add -A`, `git add .` nem `git commit -a`. Faça stage só de:

- arquivos declarados em `Arquivos:` das tarefas envolvidas;
- arquivos que os implementadores reportaram como criados/alterados;
- a própria Spec e, quando alterados, o backlog de origem e
  `docs/context/current-state.md`.

Arquivo não rastreado fora dessa lista nunca é adicionado.

## Mensagens

Conventional Commits:

| Momento | Mensagem |
|---|---|
| `/spec` gerou a Spec | `docs(spec): <título> (review)` |
| `/approve` | `docs(spec): aprova <slug>` |
| Onda do `/hands-on` | `<tipo>(<escopo>): <slug> — onda N (T1, T2)` |
| Spec concluída (`/hands-on`, `/back`, `/front`, `/recheck`) | `docs(spec): conclui <slug>` |
| `/back` ou `/front` avulso | `<tipo>(<escopo>): <resumo>` |

- `<tipo>`: `feat` por padrão; `fix`, `refactor` ou `chore` quando **todas** as tarefas envolvidas tiverem esse `Tipo:`.
- `<escopo>`: app/package (`api`, `web`, `ui`...); em Modo `single`, omita: `feat: <...>`.
- Corpo, quando houver Spec: `Spec: <caminho>` e `Cobre: FR-001, FR-002`.

## Push e PR

`git push` e `gh pr create` só com confirmação humana (ficam em `ask` nas
permissões). PR: base = branch padrão, head = `spec/<slug>`. Sem `gh`
instalado/autenticado, imprima o comando para o humano rodar.

## Working tree

Antes de começar um fluxo que commita, rode `git status --porcelain`:

- mudança **rastreada** pendente (linhas que não começam com `??`) → pare e
  peça ao humano para commitar ou guardar (`git stash`) antes;
- arquivos **não rastreados** (`??`) não bloqueiam e nunca são tocados.
````
